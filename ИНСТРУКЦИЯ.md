# ЛР №5 — инструкция по сдаче (вариант 4, Автосервис)

Проект — копия ЛР №4 в папке `lab05`, тот же Git-репозиторий (`github.com/sita32/lab04ipprpo`) и тот же Jenkins job.
Все команды выполнять в терминале из папки `lab05`.

## Что сделано

| Файл | Что изменено |
|---|---|
| `pom.xml` | зависимости `slf4j-api`, `logback-classic`; плагин `maven-checkstyle-plugin` |
| `checkstyle.xml` | правила статического анализа (см. ниже) |

| `RepairService.createOrder` | логирование создания заказа: INFO / WARN / ERROR |

| `RepairServiceTest` | 2 новых теста: повторный заказ и пустой заказ |
| `Jenkinsfile` | этапы Checkout → Build → **Static Analysis** → Test → Package |
| исходники | убраны пробелы в концах строк (иначе Checkstyle ругался) |

### Логирование создания заказа (`RepairService`)

| Уровень | Когда | Почему этот уровень |
|---|---|---|
| INFO | `Начато создание заказа o1 для автомобиля ...` и `Заказ o1 успешно создан` | обычный ход работы |
| WARN | `Заказ o1 уже существует, повторное создание отклонено` | не сбой системы, но операция отклонена — стоит обратить внимание |
| ERROR | `Ошибка создания заказа: не указан заказ или автомобиль` | ошибка обработки — заказ создать невозможно |

### Правила Checkstyle (`checkstyle.xml`)

- **LineLength** — строка не длиннее 120 символов
- **FileTabCharacter** — нельзя табуляцию, только пробелы
- **RegexpSingleline** — нельзя пробелы в конце строки
- **TypeName / MethodName / LocalVariableName / MemberName** — классы с большой буквы (`RepairService`), методы и переменные с маленькой (`createOrder`)
- **AvoidStarImport** — нельзя `import java.util.*`
- **UnusedImports** — нельзя неиспользуемые импорты
- **NeedBraces** — `if/for/while` всегда с `{ }`
- **Regexp** — запрещён `System.out.println`, нужно использовать Logger

Плагин запускается командой `mvn checkstyle:check`. Нарушения считаются ошибкой (`failOnViolation=true`, `violationSeverity=warning`) → сборка падает.

## Вопросы на защите — коротко

- **Static Analysis vs Testing**: анализ проверяет код без запуска; тесты запускают код и проверяют поведение.
- **Static Analysis vs Logging**: анализ — «что не так в коде», результат — список нарушений; логи — «что происходило при работе», результат — журнал.
- **SLF4J** — интерфейс (`Logger`, `LoggerFactory`), **Logback** — реализация, которая печатает сообщения. Можно заменить Logback, не трогая код.
- **Почему Logger, а не println**: есть уровни, формат (время, класс), настройка вывода в одном файле `logback.xml`.
- **Почему Static Analysis до Test**: дешёвая быстрая проверка — если код не по правилам, тесты и упаковку запускать незачем.
- **`{}` в сообщениях** — подстановка параметров SLF4J, строка собирается только если уровень включён.
